절차

순서는 고정이다. 사람이 손대는 칸이 강조된 칸이고, 그 앞으로는 원격이 0이다.

01

탐지

크래시·세션 오동작·정적 결함 세 종류로 분류한다. 정기 배치도, 상시 폴링도 없다.

02

유효성 확인

이미 착륙했나 · 현행 dev에 경로가 살아 있나 · 깨끗한 HOME에서도 재현되나 · 크래시 지문이 있나.

03

등급 · 배제

크래시·데이터 손실·라이브 장애만 HIGH. 배제 뷰에 걸리면 수락 이전에 떨어진다.

04

수락 — 사람

열한 슬롯 보고와 Decision block을 갖춘 카드로 올린다. 수락·거절·보류는 사람이 고른다.

05

세 게이트

maintainer_prohibition → freeze → contract/state. 첫 실패에서 단락.

06

전송 — 사람

push·PR·이슈 생성은 승인 뒤에만, 그 head sha에만 유효하다. 자동 제출은 없다.

07

원장 · 관측

다섯 필드 한 행을 갱신하고 관측 노트를 append한다. 원격 상태는 복사하지 않고 파생한다.

왜 이렇게 만들었나

"버그 찾아서 PR 내"만 시키면 draft PR 더미와 진단 로그 개선 PR이 쌓여 메인테이너 큐를 오염시킨다.

사람 게이트2개

수락과 전송은 다른 문이다

① 수락 — 이걸 퀘스트로 삼을지. ② 전송 — 실제로 원격에 낼지. ①을 통과했다고 ②가 허락된 것이 아니다. 스킬은 어느 쪽도 대신 하지 않는다.

슬롯1개

동시 진행은 하나

두 번째 accepted 행을 만들 수 없다. WIP 개수·로트 수명·토큰 예산 같은 숫자 상한은 쓰지 않고 구조로 막는다.

게이트순차 3단

막히면 원격은 0

금지 통보·동결·상태 손상 중 하나라도 걸리면 PR과 crash report 양 경로가 다 막힌다. 그동안에도 탐지·수락·로컬 기록은 정상 동작한다.

Pre-intake4단

이미 고쳐진 것은 퀘스트가 아니다

로컬 설치본은 upstream dev보다 늘 낡다. 등급 판정 전에 착륙 여부·현행 dev 경로·깨끗한 HOME 재현·크래시 지문 존재를 확인하고, 떨어지면 카드를 안 올린다.

Minimality결함 1개

설계 권한을 빌리지 않는다

한 PR은 결함 하나, 최소 수정. 정답이 둘 이상이면 그건 결함이 아니라 제품 결정이므로 코드가 아니라 별도 이슈로 내려간다.

독립 리뷰 두 번에 blocker가 남으면 멈춘다 — 세 번째 재설계는 설계가 남의 것이라는 증거다.

원장5필드

이중 기장을 하지 않는다

quest_id · source · state · pr · closure_cause. 여섯 번째 열도, candidate 같은 유사 상태도 없다. 원격 현재 상태는 읽기 전용 gh로 파생한다.

freeze3술어

동결은 감지하고 멈춘다

리뷰 없는 일괄 close · do not open 류 문구 · 내 항목이 24시간 안에 여럿 close됨. 하나라도 관측되면 전송이 0이 되고 로컬 카드로 알린다.

해제는 경과 시간이 아니라 오너가 다시 리뷰·머지하는 이벤트로만 한다.

Decision block

선택지만 나열한 카드는 카드가 아니다

선택지마다 "고르면 벌어지는 일 / 유리한 점 / 불리한 점"을 채우고 권장 하나와 근거를 단다. 근거가 부족하면 무엇이 부족한지를 적는다.

설치

스킬 파일은 곧 프롬프트다. 에이전트 실행 경로에 텍스트를 꽂는 일이니 리비전을 고정하고 바이트를 검증한다.

# 1. 리비전 고정 — 태그나 커밋 sha. 움직이는 브랜치는 쓰지 않는다
REV=v0.1.0

# 2. 스킬 디렉터리가 아니라 스테이징 경로로 받는다
curl -fsSL "https://raw.githubusercontent.com/yazzang-homelab/gjc-quest/$REV/SKILL.md" \
  -o /tmp/gjc-quest.SKILL.md
curl -fsSL "https://raw.githubusercontent.com/yazzang-homelab/gjc-quest/$REV/SHA256SUMS" \
  -o /tmp/gjc-quest.SHA256SUMS

# 3. 바이트를 검증하고, 통과한 뒤에만 설치한다
(cd /tmp && sed 's| SKILL.md$| gjc-quest.SKILL.md|' gjc-quest.SHA256SUMS | sha256sum -c -)
install -Dm644 /tmp/gjc-quest.SKILL.md ~/.gjc/agent/skills/gjc-quest/SKILL.md

# 4. 출처 증명 — 이 저장소·이 워크플로에 바이트를 결속한다
gh attestation verify /tmp/gjc-quest.SKILL.md --repo yazzang-homelab/gjc-quest

# config.yml — 참이어야 로드된다
skills.enabled: true
skills.enablePiUser: true

# 호출 (새 세션에서)
/skill:gjc-quest
  • 체크섬과 attestation을 둘 다 두는 이유. 체크섬은 파일과 같은 곳에서 오므로 그것만으로는 공급망 증명이 되지 않는다. Sigstore attestation은 바이트를 이 저장소와 이 워크플로에 결속한다. PGP 서명은 없다 — 없는 것을 있다고 말하지 않는다.
  • CI가 SHA256SUMS와 SKILL.md가 어긋나는 커밋을 거부한다. 낡은 체크섬은 없는 것보다 나쁘다 — 검증을 건너뛰는 습관을 가르치기 때문이다.
  • 설정을 켠 직후 세션에는 반영되지 않는다. 새 세션에서 호출해야 한다 — /skill:gjc-quest가 "없는 스킬"로 보이면 원인은 이것이 먼저다.
  • 별칭: gjc quest · quest scan · gjc 퀘스트 · 결함 퀘스트 · 기여할 거 있나 · 이거 PR 낼까
  • 원장과 관측 노트는 ~/.gjc/agent/state/gjc-quest-ledger.md 한 파일에 붙는다. 새 JSONL을 만들지 않는다.
  • 관측 노트는 로컬 전용이다. 저장소도 노트 내용을 담지 않는다 — 배제 뷰는 각자가 자기 관측에서 채우는 빈 뷰다.

이 규율을 실제로 지키는가

절차가 촘촘하다는 것과 매번 지켰다는 것은 다른 문제다. 그래서 원장을 그대로 공개한다.

  • 25건 중 15건은 원격 객체를 아예 만들지 않았다. 읽을 값이 있는 쪽은 이 숫자다 — 배제·미재현·제품 결정 선행으로 걸러진 것들이고, 게이트가 장식이 아니라는 증거다.
  • locator가 붙은 10건의 상태는 export 시점에 읽기 전용 gh로 하나씩 재파생했다. 마크다운에 두 번째 권위 상태를 두지 않는다는 규칙이 실물로 보이는 부분이다.
  • 관측 노트·Decision block·11슬롯 보고는 공개하지 않는다. 특정 관리자의 행동에 대한 해석이 들어 있어 공개하면 증거가 아니라 신상 문서가 된다.
  • locator 상태 이외는 자기 보고다. 보류가 정직했는지는 이 사이트가 증명하지 못한다 — 증명되는 것은 비율이 자기 유리하게 조작되지 않았다는 것뿐이다.

하지 않는 것

예외 경로를 두지 않는다.

자동 제출 — push·PR·이슈 생성은 승인 뒤에만, 그 head sha에만.
정기 배치·상시 폴링 — cron은 세션과 함께 소멸한다. 사람이 시각을 지정한 1회 보고만 예외.
허가 문의 — 메인테이너에게 "내도 되나요"를 묻지 않는다. 증거를 담은 범위 밖 결함 이슈만 예외.
재구현 — gjc crash report를 감싼다. 지문·이슈 생성을 대신 만들지 않는다.
설정 변경 · 훅 설치 — 스킬이 config.yml을 건드리지 않는다.
손상 상태 고쳐 쓰기 — 중복·손상 섹션은 보류하고 사람에게 보고한다.
이 스킬은 비공식 서드파티이며 upstream과 제휴 관계가 없다. 대상은 Yeachan-Heo/gajae-code이고 대상 브랜치는 항상 dev이며, gjc crash report·gjc notify·PR verdict 블록처럼 gjc에만 있는 표면을 전제한다. 다른 저장소에 쓰려면 그 부분을 다시 써야 한다. 기여 수용 여부는 언제나 그 저장소 관리자의 것이며, 이 문서는 절차이지 실행 권한이 아니다.
